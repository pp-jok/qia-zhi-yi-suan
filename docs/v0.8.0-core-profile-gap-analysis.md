# v0.8.0 Core Profile 链路差距分析

## 结论

v0.7 的出生输入已经能稳定产出合格的八字与星盘事实，并通过 `qualified facts` 边界进入已审计解释规则；但产品入口在 `birth_report.py` 中直接调用固定主题的 `build_interpretive_report`。因此，事实、跨体系关系和报告章节之间没有可审计的正式产品画像对象，导致不同个案仍可能落入相似的主题编排。

现有 `CoreDestinyProfile` 不是该缺口的直接答案。它是受治理的正式 primitive 发布 IR，当前发布资产没有活跃映射，设计上必须保持 `unknown`。把 candidate mapping 或旧规则伪装为该对象的正式 primitive 结论，会违反现有资产边界。

## 实际链路

```text
出生文本
  -> LocalTimeNormalizer / LocalBaziCalculator / LocalAstrologyCalculator
  -> deterministic facts + qualification
  -> extract_interpretive_signals
  -> build_interpretive_core_profile / narrative synthesis
  -> build_interpretive_report（固定主题分组）
```

`interpretive_synthesis.py` 已提供独立的八字、占星主题资料以及逐主题的 validation、tension、unresolved、non_comparable 关系；`interpretive_report.py` 没有消费这些关系来决定产品章节。`core_destiny_profile.py`、`report_planner.py` 和 `release_renderer.py` 形成了另一条严格发布路径，但只允许已批准 active mapping，故当前不会产生实质画像。

## 可复用资产

- 合格事实与双指纹：`deterministic_facts_codec.py`。
- 已审计、可追溯解释信号及其 mechanism、expression、context、限制：`interpretive_rules.py` 与 `interpretive_models.py`。
- 两体系独立 profile 与逐主题关系、张力：`interpretive_system_profiles.py`、`interpretive_synthesis.py`。
- 旧标准/精简解释报告与 CLI：兼容保留，绝不改变其语义。

## v0.8 最小闭环

新增 `audited-interpretive-cdp-v1`：它不是 formal primitive CDP，也不声称 candidate asset 已发布。它以已匹配的规则信号形成八字/占星候选、精确主题的跨体系关系、可解释的主导签名、张力/支持型动态、影子与成熟表达、生活主题和一个有证据的原型摘要。每一项都携带 signal id、rule ref、fact ref 与限制。

新 planner 只选择画像中实际存在的项目，按显著度和去重键生成 4–8 个章节；renderer 只能消费计划引用的画像条目。出生入口默认使用新模式 `core-profile-v1`，保留 `standard-interpretive-v1` 与 `concise-interpretive-v1`。

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 候选资产越界 | 新 IR 的 assurance 固定为 `audited_interpretive_rule_derived`，不写入 formal CDP 或 release manifest。 |
| 报告仍同质 | planner 以 signature/dynamic/theme 身份键去重；无证据不补齐章节。 |
| 跨体系强行一致 | 只复用已有 exact-topic relationship；单边证据保留 non-comparable。 |
| 旧接口回归 | 保留旧模式、旧 codec、旧 CLI 命令语义，并加回归测试。 |
| 文案越过事实 | 每个 reader section 带 profile refs、signal ids、限制；renderer 不接触原始事实或规则目录。 |
